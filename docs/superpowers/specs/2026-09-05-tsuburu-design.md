# tsuburu 설계

작성일: 2026-09-05

## 1. 무엇을 만드는가

hitomi.la를 검색하고 열람하는 데스크톱 애플리케이션. 실행 파일 하나를 받아
실행하면 로컬 서버가 뜨고 브라우저가 열린다. 별도 설치나 설정이 없다.

기준점이 되는 기존 프로젝트는 `project-artifact/artifact`이다. 초기 artifact은
Flutter 기반 모바일 앱이었고(조직 내 `libartifact`은 Rust로 작성된
android/ios 다운로더, `p7zip`은 flutter 바인딩), 현재의 "next gen" 리포지터리는
Docker Compose로 7개 남짓의 서비스(수집, OCR, 검색 인덱스, 키워드 그래프,
웹 뷰어)를 띄우는 TypeScript 자기호스팅 툴킷으로 전환되었다.

tsuburu는 그 반대편을 노린다.

| | artifact (next gen) | tsuburu |
|---|---|---|
| 배포 단위 | docker compose, 다중 서비스 | 실행 파일 1개 |
| 대상 사용자 | 개발자 | 일반 사용자 |
| 검색 인덱스 | 자체 구축 | hitomi의 인덱스를 원격에서 직접 읽음 |
| 첫 실행까지 | 저장소 클론, 컨테이너 빌드 | 다운로드 후 실행 |

### 목표

- 다운로드 후 즉시 검색 가능. 초기 인덱싱 대기 없음.
- 단일 정적 바이너리. 런타임 설치 요구 없음.
- Windows / macOS / Linux 지원.
- 검색 응답이 웹 사이트보다 느리지 않을 것.

### 목표가 아닌 것

- 모바일 단독 실행. 같은 네트워크에서 폰 브라우저로 접속하는 것은 부수적으로
  되지만 지원 대상으로 삼지 않는다.
- 외부 접속, 인증, 다중 사용자.
- 전체 메타데이터 스냅샷 다운로드. v1 범위 밖(11절 참고).
- OCR, 키워드 그래프, 추천 등 artifact의 분석 기능.

## 2. 형태

localhost에서 도는 단일 프로세스다.

```
[브라우저] <--HTTP--> [tsuburu 바이너리] <--HTTPS--> [hitomi]
              localhost      axum + Rust           인덱스 / 메타 / 이미지
```

브라우저가 hitomi에 직접 붙을 수 없기 때문에(CORS 및 Referer 제약) 바이너리가
중계한다. self-hosted이므로 이 중계는 사용자 자신의 기기에서만 일어나며,
운영 비용이나 제3자 노출이 발생하지 않는다.

이 구조를 택한 이유는 webview 툴체인(리눅스 WebKitGTK 편차, 플랫폼별 빌드,
코드사이닝)을 통째로 우회하면서 크로스플랫폼을 얻기 때문이다. 대가는 모바일
단독 실행이 불가능하다는 것이며, 이는 위에서 명시적으로 목표에서 제외했다.

## 3. 모듈 경계

카고 워크스페이스. 분할 기준은 **"hitomi가 포맷을 바꾸면 어디를 고치는가"** 이다.

```
tsuburu-hitomi   hitomi 프로토콜 지식 전담 (인덱스 파싱, ID 리스트, 메타, URL 규칙)
tsuburu-fetch    Fetcher 트레잇 구현 (reqwest, Range, 재시도, 동시성 제한)
tsuburu-store    로컬 상태 (즐겨찾기, 기록, 다운로드) — redb
tsuburu-server   axum (정적 자산, JSON API, 이미지 프록시)
tsuburu          실행 파일 (포트 확보, 서버 기동, 브라우저 실행, CLI)
web/             Svelte 5 + Vite + TypeScript
```

### 불변 규칙

hitomi 포맷에 대한 지식은 `tsuburu-hitomi` 밖으로 나가지 않는다. 서버와 UI는
"검색 조건을 주면 갤러리 목록이 온다"는 추상만 본다. 사이트가 변경되었을 때
수정 범위를 한 crate로 가두기 위한 것이며, 이 프로젝트에서 가장 중요한 설계
결정이다.

### `tsuburu-hitomi`는 네트워크를 하지 않는다

이 crate는 다음 트레잇에만 의존한다.

```rust
trait Fetcher {
    async fn get_range(&self, url: &str, range: Range<u64>) -> Result<Bytes>;
    async fn get(&self, url: &str) -> Result<Bytes>;
}
```

실제 응답 바이트를 픽스처로 저장해두면 네트워크 없이 파서를 테스트할 수 있다.
문서화되지 않은 바이너리 포맷을 다루는 이상 이것이 유일하게 신뢰할 수 있는
검증 수단이다.

## 4. 검색 동작

hitomi는 브라우저에서 클라이언트 사이드 검색이 돌도록 인덱스를 정적 파일로
서빙한다. tsuburu는 이 인덱스를 그대로 읽는다. 자체 인덱스를 만들지 않기
때문에 초기 다운로드가 없다.

### 정형 조건 (태그, 언어, 타입)

정렬된 갤러리 ID 배열 형태의 목록 파일이 이미 존재한다. 첫 페이지를 그리는 데
전체가 필요하지 않으므로 Range 요청으로 앞 구간만 가져온다. 페이지 이동도
해당 구간만 추가로 가져온다.

### 자유 검색어

B-tree 인덱스를 루트부터 노드 단위로 타고 내려간다. 한 번의 검색은 몇 차례의
왕복과 수 KB 전송으로 끝난다. 로컬 인덱스 없이도 빠른 이유다.

### 복합 조건

각 조건이 만들어낸 정렬된 ID 배열을 교집합으로 접는다. 갤로핑(지수 탐색)
교집합으로 구현한다. SIMD 교집합이나 로어링 비트맵으로의 전환은 **프로파일링
결과 이 구간이 병목으로 확인된 뒤에만** 한다. 실제 병목은 네트워크 왕복일
가능성이 높으며, 재보지 않고 최적화하면 효과 없는 코드만 남는다.

### 캐시

인덱스 노드는 메모리 LRU와 디스크에 캐시한다. 상위 노드는 모든 검색에서
동일하게 사용되므로 기동 시 확보해 상주시킨다. 하위 탐색은 예측 가능한 구간을
묶어 요청 횟수를 줄이고, HTTP/2 커넥션을 재사용하며, 동일 구간에 대한 동시
요청은 합친다.

### 오프라인 범위

로컬 DB에 쌓이는 것은 **사용자가 직접 만진 것**뿐이다: 열람 기록, 즐겨찾기,
다운로드한 작품. 이 범위 안에서는 오프라인 검색이 된다. 그 밖의 검색은
네트워크를 필요로 한다.

## 5. 이미지 경로

hitomi는 이미 avif/webp를 서빙하고 현재 브라우저는 두 포맷을 모두 지원한다.
따라서 서버는 **디코드도 리사이즈도 하지 않고 바이트를 그대로 흘린다.**
썸네일 역시 원본 그대로 전달한다.

이미지 처리 crate를 넣지 않는 것만으로 바이너리 크기와 메모리 사용량이 크게
줄어든다. 서버가 하는 일은 Referer 등 필요한 헤더를 붙이고, 스트리밍하고,
동시 요청 수를 세마포어로 조이는 것뿐이다.

## 6. 기술 스택

### 백엔드

| 역할 | 선택 | 근거 |
|---|---|---|
| 에디션 | Rust edition 2024, `rust-toolchain.toml`로 버전 고정 | 재현 가능한 빌드 |
| 런타임 | tokio (multi-thread) | 네트워크 I/O 지배적 |
| 웹 서버 | axum + tower-http | hyper 계열 일관성 |
| HTTP 클라이언트 | reqwest (rustls-tls, HTTP/2, default-features off) | OpenSSL 배제 |
| TLS | rustls | C 의존성 없음, 크로스컴파일 용이 |
| 직렬화 | serde / serde_json | — |
| 로컬 저장 | redb | 순수 Rust 임베디드 KV |
| 자산 임베드 | rust-embed (brotli) | 프론트 dist를 바이너리에 포함 |
| 캐시 | quick_cache 또는 직접 구현한 LRU | 인덱스 노드용 |
| 에러 | thiserror (crate) / anyhow (bin) | 관례 |
| 로깅 | tracing + tracing-subscriber | 왕복 횟수 계측에 사용 |
| 경로 | directories | OS별 설정/캐시 디렉터리 |
| 브라우저 실행 | open | 3-OS 처리 |
| CLI | clap | 마일스톤 1 |
| 동시성 제어 | tokio::sync::Semaphore | 별도 crate 불필요 |

C 의존성을 두지 않는 것이 스택 선택의 일관된 기준이다. 정적 링크와 크로스
컴파일이 조건 없이 성립해야 단일 바이너리 배포가 유지된다. redb를 SQLite보다
우선한 이유도 동일하다. 로컬 라이브러리 관리 기능이 복합 질의를 요구할 만큼
커지면 재검토한다.

### 프론트엔드

Svelte 5(runes) + Vite + TypeScript.

컴포넌트 라이브러리를 사용하지 않는다. 화면은 검색/그리드/뷰어 셋뿐이고,
이미지 뷰어의 요구사항(키보드 네비게이션, 선디코드, 프리페치)은 어떤
라이브러리로도 대체되지 않아 직접 작성하게 된다. 라우터도 해시 기반으로 직접
둔다. 스타일은 CSS 커스텀 프로퍼티.

갤러리 그리드는 항목이 수만 개에 이르므로 가상 스크롤이 필요하다.
`content-visibility`와 IntersectionObserver, `img.decode()`를 사용해 직접
구현한다.

### 빌드 · 배포

- 태스크 러너: `just`
- CI: GitHub Actions — 프론트 빌드 → rust-embed → 3-OS 바이너리
- 릴리스: `cargo-dist`
- 타겟: macOS(x86_64, aarch64), Windows(x86_64-msvc), Linux(x86_64-gnu, 가능하면 musl)
- 릴리스 프로파일: `lto = "fat"`, `codegen-units = 1`, `opt-level = "z"`,
  `panic = "abort"`, strip

코드사이닝은 하지 않는다. macOS에서 "확인되지 않은 개발자" 경고가 발생하며,
README에 우클릭-열기 절차를 안내한다. self-hosted 도구의 성격상 수용 가능한
마찰로 판단했다.

## 7. 실패를 전제로 한 설계

hitomi가 인덱스 포맷을 변경하면 앱은 반드시 깨진다. 설계상의 질문은 깨지느냐가
아니라 깨졌을 때 사용자가 무엇을 보느냐이다.

- 인덱스 버전을 먼저 확인한다. 알 수 없는 버전이면 파싱을 시도하지 않는다.
- "사이트 구조가 변경되어 업데이트가 필요합니다"라고 명시적으로 표시한다.
  잘못된 결과나 빈 화면을 내지 않는다.
- 네트워크 오류와 포맷 오류를 구분해 표시한다. 사용자가 취할 조치가 다르다.
- 실제 응답 바이트를 픽스처로 보관하고 파서 테스트에 사용한다.

## 8. 테스트

- `tsuburu-hitomi`: 저장된 응답 픽스처에 대한 단위 테스트. 네트워크 불필요.
  이 crate가 테스트 커버리지의 중심이다.
- 교집합 알고리즘: 단위 테스트. 최적화 전후의 동등성 확인.
- `tsuburu-server`: API 계약 테스트. Fetcher를 목으로 교체.
- 프론트: 최소한. 그리드 가상화와 뷰어 키보드 조작 정도.
- 실제 hitomi에 붙는 통합 테스트는 별도 표시를 두어 기본 실행에서 제외한다.
  네트워크와 외부 사이트 상태에 의존하므로 CI를 불안정하게 만든다.

## 9. 마일스톤

1. **인덱스 정복.** `tsuburu search "<query>"` CLI가 갤러리 ID 목록을 출력한다.
   UI 없음. 이 단계가 성립하지 않으면 프로젝트 전체가 성립하지 않으므로
   최우선이다. 이 단계에서 실제 왕복 횟수와 전송량을 측정해 12절의 성능 목표를
   확정한다.
2. 갤러리 메타데이터 조회, 이미지 프록시. 브라우저에서 작품 하나를 끝까지 본다.
3. 검색 UI, 가상 스크롤 그리드, 태그 필터.
4. 즐겨찾기, 열람 기록, 다운로드 (redb).
5. 단일 바이너리 릴리스, 3-OS CI, 첫 실행 시 연령 고지.

## 10. 법적 · 콘텐츠 고려사항

대상 사이트는 성인 콘텐츠를 포함한다. 첫 실행 시 연령 확인 고지를 표시한다.

tsuburu는 콘텐츠를 호스팅하거나 재배포하지 않는다. 사용자 기기에서 실행되며
사용자 본인의 요청만 중계한다. 요청량은 세마포어로 제한해 대상 사이트에
과도한 부하를 주지 않는다.

## 11. 의도적으로 미룬 것

- **전체 메타데이터 스냅샷 다운로드.** 오프라인 전체 검색과 고급 질의가
  가능해지지만 수백 MB 다운로드와 주기적 동기화가 필요하다. 원격 인덱스만으로
  충분한지 먼저 확인한 뒤, 실제로 부족하면 그때 추가한다.
- SIMD 교집합, 로어링 비트맵 — 측정 후 판단.
- 모바일 셸.
- 다운로드한 작품에 대한 복합 태그 검색 (필요해지면 저장 계층 재검토).

## 12. 성능 목표

마일스톤 1에서 실제 측정 후 확정한다. 측정 없이 수치를 정하지 않는다.

측정 항목:
- 검색어 1개 질의의 HTTP 왕복 횟수 및 총 전송 바이트
- 캐시 미적중 / 적중 시 검색 응답 시간
- 태그 3개 AND 질의의 교집합 계산 시간
- 릴리스 바이너리 크기, 유휴 상태 메모리 사용량
