# artifact 아티팩트 통합 설계

작성일: 2026-09-09
선행 스펙: `2026-09-07-dialogue-search-design.md`

## 1. 무엇이 있었나

사용자가 artifact에서 제공하는 아티팩트 두 묶음을 갖고 있었다. 대사 검색 스펙이
"한 사람이 갈고 나머지가 받는다"고 쓴 그 결과물이다.

### `llm-search-index/` (3.9 GB)

| 파일 | 내용 |
|---|---|
| `compact-metadata.bin` + `-offsets.bin` (1.5 GB) | **한국어 108,369작품의 인식 텍스트**, 2,537,826 청크. 청크 = 3페이지 창(2페이지 간격, 1페이지 겹침)의 줄들 |
| `faiss-sq8.index` (2.6 GB) | 청크별 Qwen3-Embedding-4B 임베딩(1024차원, SQ8). 뜻으로 찾는 용도. **질의를 같은 4B 모델로 임베딩해야 하므로 이번 범위 밖** |
| `manifest.json` 등 | 스키마. 원본 임베딩 파일은 없음 |

레코드: `i64 work_id, u16 page_count, u32 text_len`, 페이지 번호 `u32 × page_count`(1-based),
UTF-8 텍스트(줄바꿈 구분). 같은 작품의 청크는 연속.

### `artifact/` (5.1 GB)

| 파일 | 내용 | 판단 |
|---|---|---|
| `data.db` (2.2 GB, SQLite) | `HitomiColumnModel` **2,957,710행**(존재 1,464,362), 제목·타입·언어·작가·그룹·시리즈·캐릭터·태그·발행일·페이지 수·썸네일. Id 4,043,071까지(2026-07 중순) | **가져옴** |
| `merged-0.fscm` (3.1 GB) | artifact-message-search의 스캔 포맷. 45,904,212줄, 줄마다 페이지·bbox·신뢰도 | **제외** — `message` 필드가 한글이 아니라 두벌식 키 입력열(`dkssudgktpdy` = 안녕하세요)이고 이 빌드에는 원문(`raw`)이 없다 |
| `graph.csv` (198 MB) | 작품별 키워드 상위 100(TF-IDF) 4,064,567행 | 보류 |

## 2. 무엇이 바뀌나

**대사 검색의 그라인더가 주역에서 보조로 내려간다.** 한국어 전체는 파일에서
30초에 들어온다. 그라인더는 스냅샷 이후의 신작과 다른 언어에만 쓴다.

**메타데이터 스냅샷이 생긴다.** v1 스펙이 일부러 피했던 "전체 스냅샷"이다.
받을 필요가 없어졌으니 피할 이유도 없다. 스냅샷이 덮는 갤러리의 카드는
네트워크를 타지 않고, 한국어 제목·작가·시리즈·캐릭터가 오프라인에서
검색된다. 스냅샷보다 새 갤러리는 전과 같이 네트워크로 간다.

## 3. 가져오기

```
tsuburu import-artifact <llm-search-index/>   # 대사 텍스트 → dialogue.redb
tsuburu import-meta   <data.db>             # 메타데이터   → meta.redb
```

둘 다 서버를 끄고 실행한다(redb는 한 프로세스만 연다). `import-artifact`은
UI(Dialogue 탭)에서도 배경 작업으로 실행할 수 있다.

`data.db`는 FTS5 가상 테이블을 포함한 SQLite라 SQL 엔진이 필요하다. C 라이브러리나
큰 Rust 크레이트를 한 번 쓰고 마는 가져오기를 위해 바이너리에 넣지 않고,
로컬의 `sqlite3` 명령으로 행을 흘려 받는다(단위/레코드 구분자 `0x1f`/`0x1e`).
값 정리: 타입 표기 통일(`artist CG`/`artist cg` → `artistcg`), 발행일은
문자열과 .NET 틱 두 형식, 썸네일 URL에서 64자 해시만.

실측 (M4 Pro): 대사 108,340작품 **31초**, 메타 1,464,362작품 **260초**.

## 4. 대사 검색을 코퍼스 규모에 맞게

108k 작품, 1.5 GB 텍스트를 질의마다 훑는다. 처음 구현(작품마다 deflate 해제 +
JSON 파싱 + 자모 문자열 정규화 + 트라이그램 집합)은 **4~6초**였다. 세 가지를
바꿨다.

- **페이지 인코딩을 바이너리로, 압축을 LZ4로.** 스캔 경로에 JSON이 없다.
- **매치 코드를 저장 시점에 계산해 둔다.** 자모 하나를 바이트 하나
  (`0x80..=0xC3`, ASCII와 겹치지 않음)로, ASCII는 소문자로. 한 음절이 UTF-8
  자모열의 9바이트 대신 2~3바이트이고, 질의 때 정규화가 없다.
- **퍼지 점수를 한 번의 훑기로.** 질의의 6바이트 n-gram(≈두 음절)을 64K비트
  집합에 넣고, 페이지의 모든 창을 해시해 대조한다. 후보마다 할당이 없다.
  자모 3개 창은 한국어 페이지 어디에나 있어 무관한 페이지가 0.8을 받았다;
  두 음절 창으로 바꾸자 사라졌다.

- **코드를 별도 테이블에 둔다.** 스캔은 코드 테이블만 읽고, 적중한 페이지의
  텍스트만 따로 꺼낸다. 질의마다 텍스트 1.5 GB를 풀 이유가 없다.
- **스레드 분할은 ID 범위가 아니라 개수로.** 한국어 작품은 최근 ID에 몰려
  있어 ID 범위로 나누면 한 스레드가 대부분을 맡는다.
- **정확 일치를 먼저 훑고, 모자랄 때만 퍼지.** 퍼지의 문턱은 질의의 반쪽
  (긴 질의는 1/4)이 그대로 들어 있는지다. OCR 오독이나 잘못 기억한 낱말은
  조각 하나를 깨고 나머지를 남기지만, 무관한 페이지에 세 음절이 연달아 있을
  일은 드물다. 자모 3개 창 겹침만으로는 무의미한 질의도 0.6을 받았다.

실측 (M4 Pro, 108,340작품): **정확 일치만 0.36 s, 퍼지 포함 0.6 s.** 처음
구현의 4~6 s에서 열 배 가까이 줄었다.

## 5. 메타 저장소

`meta.redb`: `works`(id → LZ4 JSON), `titles`(id → 제목, 제목 스캔용),
`terms`(멀티맵 `"tag:glasses"` → ids). 용어 키는 정렬돼 있으므로 접두 범위
스캔이 곧 자동완성이다(`artist:kes` → `artist:keso`).

검색: 용어와 필터는 집합 교집합, 제목은 자모 정규화 부분 문자열(띄어쓰기
무관). 자유 텍스트 `q`는 제목 매치와 통째 용어 매치의 합집합. 결과는 ID
내림차순(최신순) — 스냅샷에는 인기도가 없다.

## 6. 화면

- 검색창에 범위 선택: **hitomi tags** / **local titles & artists**. 스냅샷이
  없으면 선택이 나타나지 않는다.
- Dialogue 탭에 artifact 디렉터리 가져오기와 진행률.
- 카드는 스냅샷이 있으면 거기서 그린다.

## 7. 하지 않은 것

- FAISS 의미 검색. 질의 임베딩에 4B 모델이 필요하다. 나중에 판단.
- `graph.csv` 키워드. "비슷한 작품"에 쓸 수 있으나 지금 필요가 없다.
- `merged-0.fscm`의 줄 단위 페이지·bbox. 텍스트가 키 입력열이라 표시에 못
  쓰고, 청크의 3페이지 창으로도 독자를 근처로 보낼 수 있다.
