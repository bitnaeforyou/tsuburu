# tsuburu 확장 설계 — 라이브러리, 정렬·필터, 한국어 검색

작성일: 2026-09-07
선행 스펙: `docs/superpowers/specs/2026-09-05-tsuburu-design.md`

## 1. 무엇을 더하는가

v1은 검색하고 읽는 것만 한다. 여기서 세 가지를 더한다.

- **라이브러리** — 즐겨찾기, 읽음 기록, 이어보기
- **정렬과 필터** — 인기순/날짜순, 언어·타입·태그 필터
- **한국어 검색** — 한국어 입력을 hitomi의 영어 태그로 보정

셋은 서로 의존하지 않는다. 각각 따로 붙이고 따로 되돌릴 수 있다.

구현 순서는 라이브러리 → 정렬·필터 → 한국어다. 라이브러리가 가장 독립적이고,
정렬·필터는 검색 엔진을 건드리므로 한국어보다 먼저 안정화되는 편이 낫다.

## 2. 조사 결과

착수 전에 hitomi가 실제로 무엇을 제공하는지 확인했다(2026-09-07).

### 2.1 정렬과 필터는 이미 존재한다

`.nozomi` 파일은 빅엔디언 i32 갤러리 ID 배열이며, 파일마다 정렬 기준이 다르다.
전부 200을 반환하는 것을 확인했다.

| 용도 | 경로 | 크기 |
|---|---|---|
| 날짜순 전체 | `index-all.nozomi` | 4.8 MB |
| 날짜순 언어별 | `index-korean.nozomi` | 397 KB |
| 인기순 | `popular/{today,week,month,year}-{lang}.nozomi` | 0.9–4.8 MB |
| 타입별 | `type/{doujinshi,manga,artistcg,...}-{lang}.nozomi` | 0.85–2.7 MB |
| 태그별 | `tag/{tag}-{lang}.nozomi` | 23–360 KB |
| 시리즈별 | `series/{name}-{lang}.nozomi` | 19 KB |

**언어 필터는 파일 이름에 들어 있다.** 별도 교집합 연산이 필요 없다.
`artist/`, `character/`, `group/` 접두사는 시험한 이름에서 404였다. 실제 이름을
확인하기 전까지 지원 목록에 넣지 않는다.

### 2.2 한국어 사전의 실제 커버리지

`project-artifact/tag-info`(Unlicense, 퍼블릭 도메인)에 영어→한국어 매핑이 있다.
값에 한글이 실제로 들어 있는 비율을 세었다.

| 영역 | 항목 수 | 한국어 있음 |
|---|---|---|
| 태그 `female:` | 583 | 474 (81 %) |
| 태그 `male:` | 502 | 226 (45 %) |
| 시리즈 | 5,065 | 2,794 (55 %) |
| 캐릭터 | 19,048 | 4,440 (23 %) |
| 작가·그룹 등 | 32,431 | 276 (0.9 %) |

**태그 검색은 잘 되고, 작가 이름 검색은 사실상 되지 않는다.** 데이터가 없어서
생기는 한계이므로 코드로 메울 수 없다. 설계는 이 사실을 감추지 않고 화면에
드러내는 쪽을 택한다(4절).

역방향으로 뒤집으면 한국어 한 낱말이 영어 여러 개에 대응하는 경우가 290건
있다(예: `파이어 엠블렘` → `fire emblem`, `fire emblem if`).

## 3. 정렬과 필터

### 3.1 두 개의 경로

**검색어가 없을 때**(태그·타입·언어만 지정) 해당 `.nozomi`를 그대로 페이징한다.
정렬은 어떤 파일을 고르느냐로 결정된다. 첫 페이지에 필요한 것은 앞의 25개뿐이
므로 Range로 100여 바이트만 읽는다. 현재의 검색보다도 싸다.

**검색어가 있을 때** 기존 B-tree로 ID 집합을 얻는다. 이 결과는 이미 날짜
내림차순이므로 날짜순 정렬은 추가 비용이 없다. 인기순을 요청한 경우에만
인기 `.nozomi`를 청크 단위로 읽으며 결과 집합에 있는 ID만 골라 한 페이지를
채운다.

### 3.2 인기순 재정렬의 비용

결과가 목록 전체에 고르게 흩어져 있으므로 대개 싸다. 결과가 5,000건이고 인기
목록이 950,000건이면 190개마다 하나씩 걸리므로 25개를 채우는 데 20 KB 정도만
읽는다.

**결과가 좁으면 비싸다.** 수십 건짜리 결과를 인기순으로 정렬하려면 인기 목록을
거의 전부(최대 3.8 MB) 훑어야 한다. 이 경우를 막지 않고 그대로 수행한다. 한
번이고, 캐시되고, 사용자가 요청한 동작이기 때문이다. 대신 청크 단위로 읽어
조기에 종료할 수 있게 하고, 진행 중임을 UI에서 알린다.

### 3.3 필터 조합

- 언어: `.nozomi` 파일 이름으로 해결. 비용 없음.
- 타입: `type/{type}-{lang}.nozomi`와 교집합. 검색어가 없으면 그 자체가 목록이다.
- 태그: `tag/{tag}-{lang}.nozomi`. 검색어 경로와 동일하게 교집합으로 접는다.

교집합은 기존 갤로핑 구현을 그대로 쓴다.

## 4. 한국어 검색

### 4.1 사전 만들기

`tag-info`의 JSON 세 개(`result-korean-tag`, `result-korean-series`,
`result-korean-character`)와 `result-korean-merge`를 뒤집어 한국어 → 영어
역인덱스를 만든다. 저장소에 생성 결과만 vendoring하고, 원본 JSON은 두지 않는다.

형식은 한 줄에 `한국어\t영어1\t영어2...`인 TSV로, 빌드 시점에
`include_str!`로 임베드한다. 원본 1.1 MB가 200 KB 남짓으로 줄어 바이너리는
3 MB 아래를 유지한다.

### 4.2 동작

입력의 각 낱말에 대해 사전을 찾는다. 찾으면 영어로 바꿔 검색하고, 못 찾으면
입력 그대로 검색한다. 어느 쪽이든 **무엇으로 바뀌었는지 화면에 표시한다.**

```
입력:  거유 안경 시와스노오키나
표시:  거유 → female:big breasts   안경 → female:glasses   시와스노오키나 (번역 없음)
```

작가 이름이 왜 안 나오는지 사용자가 화면에서 바로 알 수 있어야 한다. 조용히
치환하면 "이 앱은 작가 검색이 안 된다"가 아니라 "이 앱은 고장났다"로 보인다.

후보가 여럿인 낱말은 첫 후보를 기본으로 쓰되, 칩을 눌러 다른 후보로 바꿀 수
있다. 후보 순서는 사전 생성 시 고정한다.

### 4.3 하지 않는 것

- 형태소 분석, 자모 분해, 오타 교정. 사전에 있는 낱말을 그대로 찾는 것까지만 한다.
- 번역 API 호출. 오프라인 동작과 단일 바이너리를 깨뜨린다.
- 한국어 → 일본어. hitomi의 검색 인덱스는 영어 태그 기준이므로 일본어로 바꿀
  이유가 없다.

## 5. 라이브러리

### 5.1 저장소

`tsuburu-store` crate. redb 파일 하나를 OS 표준 애플리케이션 데이터 디렉터리에
둔다(`directories` crate). 경로는 로그에 남긴다.

테이블 셋:

- `favorites`: `id -> { added_at, title, thumbnail_hash, pages, language }`
- `history`: `id -> { last_seen_at, last_page, pages, title, thumbnail_hash }`
- `meta`: 스키마 버전 등

즐겨찾기와 기록에 **카드 요약을 함께 저장한다.** 목록을 그리려고 갤러리 메타
JSON을 다시 받으면(한 건에 최대 230 KB) 목록 한 화면에 수 MB가 나간다. 요약을
들고 있으면 오프라인에서도 목록이 보인다.

### 5.2 이어보기

뷰어에서 현재 페이지가 바뀌면 기록에 저장한다. 페이지를 넘길 때마다 쓰면
디스크가 시끄러우므로 디바운스한다(1초). 같은 갤러리에 다시 들어가면 마지막
위치를 알리고 이동할 수 있게 한다. 자동으로 점프하지는 않는다 — 처음부터 보려는
경우를 빼앗지 않기 위해서다.

### 5.3 API

```
GET    /api/favorites                 즐겨찾기 목록 (최근 추가순)
PUT    /api/favorites/{id}            추가 (본문에 카드 요약)
DELETE /api/favorites/{id}            삭제
GET    /api/history                   읽음 기록 (최근순)
PUT    /api/history/{id}              진행 상황 갱신 { page }
DELETE /api/history                   전체 삭제
```

## 6. 화면

헤더에 검색 / 즐겨찾기 / 기록 세 개의 경로를 둔다. 라우트는
`#/`, `#/favorites`, `#/history`.

검색 화면에는 정렬 선택(날짜순, 인기순 오늘/주/월/년)과 언어·타입 필터를 둔다.
선택은 URL 해시에 담아 뒤로가기와 새로고침이 동작하게 한다.

카드에 즐겨찾기 별을 단다. 기록에 있는 카드는 읽은 지점을 진행 막대로 표시한다.

## 7. 오류 처리

기존 원칙을 그대로 따른다. 포맷 변경과 네트워크 오류를 구분한다. 저장소 오류는
세 번째 종류로 추가한다 — 디스크가 가득 찼거나 파일이 잠긴 경우이며, 검색은
계속 동작해야 한다. 즐겨찾기를 못 쓴다고 앱 전체가 멈추면 안 된다.

## 8. 테스트

- `tsuburu-store`: 임시 디렉터리에 redb를 열어 CRUD와 스키마 버전 처리를 검증.
- 한국어 사전: 생성된 TSV에 대해 알려진 낱말의 변환을 검증. 모호한 낱말의 후보
  순서가 고정인지 확인.
- 정렬·필터: `.nozomi` 페이징과 인기순 재정렬을 목 픽스처로 검증. 좁은 결과에서
  조기 종료가 동작하는지 포함.
- 실사이트 테스트에 인기순 정렬과 타입 필터를 추가한다.

## 9. 의도적으로 하지 않는 것

- 다운로드와 오프라인 열람. 다운로드 큐·재시도·디스크 관리가 따라붙어 분량이
  크게 늘어난다. 별도 계획으로 미룬다.
- 작가·캐릭터·그룹 `.nozomi` 경로. 실제 이름 형식을 확인하기 전까지 넣지 않는다.
- 즐겨찾기 동기화, 내보내기/가져오기.
