# tsuburu 대사 검색 설계

작성일: 2026-09-07
선행 스펙: `2026-09-05-tsuburu-design.md`, `2026-09-07-library-filters-korean-design.md`

## 1. 문제

"몇 년 전에 읽었던 작품을 대사 한 줄로 찾는다." hitomi의 인덱스는 제목·태그만
담고 있어 대사로는 찾을 수 없다. 대사를 얻으려면 페이지 이미지를 받아 OCR을
돌려야 한다.

원본 그 구현은 이것을 GPU(TensorRT)와 Docker, 로컬 LLM 교정으로 풀었다. 한국어
작품만 대상으로 했고 100작품 5,926페이지를 133초에 처리했다(44.65 p/s).

## 2. 측정 (2026-09-07, Apple M4 Pro)

### 2.1 OCR 처리량 — macOS Vision

| 설정 | 처리량 | 인식 글자 | 비고 |
|---|---|---|---|
| accurate, 교정 켬, 원본 | 4.06 p/s | 7,815 | 기준 |
| accurate, 교정 켬, 병렬 12코어 | 4.76 p/s | — | **코어를 늘려도 안 오른다.** Neural Engine에서 직렬화 |
| accurate, **교정 끔**, 원본 | 7.65 p/s | 7,815 | 텍스트 동일, 1.9배 |
| accurate, 교정 끔, **75 %** | **11.33 p/s** | 7,362 (−6 %) | 채택 |
| accurate, 교정 끔, 50 % | ~15 p/s | 5,700 (−26 %) | 작은 글씨가 통째로 사라짐. 폐기 |
| fast | 51.6 p/s | 쓰레기 | 한글을 라틴 문자로 읽음(`04DFoI`). 폐기 |
| 영역 감지 → 잘라서 인식 | 6.11 p/s | −16 % | 요청 오버헤드가 절감분을 초과. 폐기 |

교정을 끄면 시간이 절반으로 줄고 인식 결과는 같다. 교정은 문장 자연스러움을
위한 것이라 검색 매칭에는 필요 없다.

### 2.2 코퍼스 — 한국어

| 타입 | 작품 수 | 평균 페이지(표본 40) | 페이지 총계 |
|---|---|---|---|
| doujinshi | 66,803 | 35.6 | 약 238만 |
| manga | 21,207 | 80.9 | 약 172만 |
| artistcg | 10,485 | — | 대사 없음, 제외 |
| imageset | 823 | — | 대사 없음, 제외 |

페이지당 평균 **245 KB**(실측 20장). 표지에만 `avifbigtn`(17 KB)이 있고 본문에는
축소판이 없다. 본문 OCR에는 원본을 받아야 한다.

### 2.3 규모

구현 후 실제 갤러리(32장, 8.1 MB)로 단계별 시간을 쟀다.

| 구간 | 시간 | 비고 |
|---|---|---|
| 페이지 다운로드 | 6.4 s | **CDN이 연결당 약 150 KB/s로 제한.** 4병렬 합산 1.2 MB/s |
| OCR | 다운로드와 겹침 | 다운로드가 끝난 뒤 남은 배출은 0.3 s |

**병목은 OCR이 아니라 CDN이다.** 이 연결에서 얻을 수 있는 총 속도가
1.2 MB/s 안팎이므로 3 MB/s 상한은 실제로는 닿지 않는다.

| | doujinshi | + manga |
|---|---|---|
| 다운로드 (1.2 MB/s) | 135시간 ≈ 5.6일 | 230시간 ≈ 10일 |
| OCR (11.33 p/s, 겹침) | 58시간 | 100시간 |
| 첫날 밤(8h) 커버 | 약 1,700편 | — |

전체 코퍼스는 이 기계와 회선으로 **일주일 남짓**이고, 첫날 밤에는 인기 상위
1,700편 정도가 들어온다. 따라서 "다 훑는다"가 아니라 "읽었을 법한 순서로
훑는다"로 문제를 바꾼다(3절).

## 3. 방법론: 확률 질량 순서

사용자가 읽은 작품은 균등 분포하지 않는다. 조회수는 멱법칙을 따르므로 인기 상위
소수가 열람의 대부분을 차지한다. **인기순으로 색인하면 첫날 밤에 적중 확률의
과반을 확보한다.**

진행률은 편 수가 아니라 **인기 상위 몇 %까지 덮였는가**로 표시한다. "못 찾음"이
"없음"인지 "아직"인지 사용자가 읽을 수 있어야 한다.

### 3.1 후보 공급원 — 같은 큐, 다른 우선순위

1. **과거 기록 가져오기** (우선순위 최고). 그 앱의 열람 기록 DB, 브라우저
   히스토리의 `hitomi.la/.../-{id}.html`. 짐작이 아니라 사실로 후보를 좁힌다.
   수백 편이면 한 시간에 끝난다.
2. **사냥 조건**. 태그·언어·시기로 좁혀 앞에 끼워 넣는다.
3. **인기순 배경 색인**. `popular/year-korean.nozomi` 순서로, 앱이 켜져 있는
   동안 조용히 돈다. doujinshi를 먼저, manga를 나중에.

## 4. 파이프라인

```
큐(redb) → 갤러리 메타 → 페이지 다운로드(3 MB/s 상한) → 디코드 → 75 % 축소
        → OCR(accurate, 교정 끔) → 텍스트 기록 → 이미지 폐기 → 체크포인트
```

- **다운로드 상한 3 MB/s.** OCR이 11.33 p/s × 245 KB ≈ 2.8 MB/s만 소화하므로
  그 이상 받아봐야 쌓인다. 실측 CDN 속도(1.2 MB/s)가 상한보다 낮아 보통은
  닿지 않지만, 회선이 좋은 환경에서 예의를 지키는 안전판으로 둔다.
- **그라인더 전용 커넥션 풀.** 페이지 다운로드가 인덱스 예열이나 사용자의
  열람 요청과 세마포어를 다투면 양쪽 다 느려진다(실측: 기동 직후 메타데이터
  조회에 7.7 s).
- **이미지는 OCR 직후 버린다.** 디스크에 남는 것은 텍스트뿐이다.
- **체크포인트.** 작품 단위로 완료를 기록해 중단·재개가 된다. 페이지 중간에
  끊기면 그 작품은 다시 한다.
- **기본은 꺼짐.** 실행하자마자 남의 서버에 수십 시간 부하를 거는 앱이 되면
  안 된다. 설정에서 켠다.

### 4.1 OCR 추상화

```rust
trait Ocr {
    /// 인코딩된 이미지 바이트(AVIF 등)를 그대로 받는다. 디코드와 축소는
    /// 백엔드가 가장 싸게 할 수 있는 방법으로 한다.
    fn recognize(&self, encoded: &[u8]) -> Result<Vec<Line>, OcrError>;
}
```

macOS는 Vision(`objc2-vision`)이며, ImageIO의 썸네일 디코드로 AVIF를 전체
해상도로 펼치지 않고 바로 75 % 크기로 얻는다. Windows는 `Windows.Media.Ocr`,
리눅스는 tesseract. **모델 파일은 싣지 않는다.** OS가 가진 것을 부른다. 1차
구현은 macOS만 하고 나머지는 "이 플랫폼에서는 대사 색인을 지원하지 않습니다"를
명확히 낸다.

인식된 줄은 말풍선 단위로 묶어 순서를 정한다. 행 높이만으로 정렬하면 같은
높이에 있는 두 말풍선이 뒤섞여 구절이 끊기고 정확 일치가 깨진다(실측). 가까이
붙고 가로로 겹치는 줄을 한 말풍선으로 묶고, 말풍선 안은 위에서 아래로,
말풍선끼리는 위에서 아래·오른쪽에서 왼쪽으로 읽는다.

## 5. 저장과 검색

역색인을 만들지 않는다. 그 구현의 `그 프로젝트의 메시지 검색`가 전체 코퍼스를 압축
포맷 그대로 훑어 168 MB로 도는 것을 확인했다. 형태소 분석기도 bigram 색인도
필요 없다.

### 5.1 저장소와 샤드

**살아 있는 저장소는 redb 파일 하나**(`dialogue.redb`)다. 갤러리마다 페이지
텍스트를 deflate로 압축해 한 레코드로 두고, 작업 큐와 같은 트랜잭션으로
커밋한다. 검색은 이 테이블을 훑는다.

**샤드는 교환용 스냅샷 포맷**이다. 갤러리 ID 구간 하나를 버전 헤더 + deflate
JSON으로 담고(`flate2`의 순수 Rust 백엔드), 파일 이름에 내용 해시를 넣어
주소화한다. 이름과 내용이 어긋나면 열지 않는다.

해시 주소화의 목적은 **공유하기 위해서**다. 한 사람이 전체를 돌린 샤드를
나머지 전원이 받으면 각자의 일주일이 사라진다.

내보내기(`POST /api/dialogue/export`)는 갤러리 ID 10만 단위로 파일을 쓰고,
가져오기(`POST /api/dialogue/import`)는 이름의 해시를 검증한 뒤 **이 기계에
없는 갤러리만** 채운다. 내보낼 때 `background_only`를 켜면 기록 가져오기·
사냥으로 색인한 갤러리는 제외된다 — 그것은 사용자가 무엇을 읽었는지를
드러내므로 공유 파일에 들어가면 안 된다.

전송 수단(HTTP, 토렌트, 파일 복사)과 조율 서버는 이 스펙 범위 밖이다.

### 5.2 매칭

- 질의와 본문 모두 한글을 **자모로 분해**해 비교한다. OCR이 받침 하나를
  틀려도 매칭된다.
- 자모열의 n-gram(3) 겹침으로 점수를 매기고, 정확 부분일치는 최상위로 올린다.
- 결과는 작품 단위로 묶고, 작품 안에서 가장 잘 맞는 페이지와 앞뒤 줄을 보여준다.

### 5.3 확인 재OCR

적중한 페이지 한 장만 원본 해상도 + 교정 켬으로 다시 OCR해 깨끗한 발췌를
보여준다. 비용은 한 장이다.

## 6. 화면

- 상단 탭에 **Dialogue** 추가.
- 검색창 + 결과(작품 카드, 페이지 번호, 발췌).
- 항상 보이는 **색인 진행률**: "인기 상위 12 % · 9,120편 · 마지막 갱신 3분 전".
- 설정: 색인 켜기/끄기, 대상(doujinshi/manga), 다운로드 상한, 과거 기록 가져오기.

## 7. 실패 처리

- OCR 실패 페이지는 건너뛰고 기록한다. 작품 전체를 버리지 않는다.
- 이미지 404(경로 회전)는 기존 프록시와 같은 재시도 규칙을 쓴다.
- 지원하지 않는 플랫폼에서는 탭 자체를 "지원 안 함"으로 표시한다.
- 디스크 부족은 색인을 멈추고 알린다. 검색은 계속 된다.

## 8. 테스트

- OCR 트레잇: 목 구현으로 파이프라인 테스트. Vision 자체는 실기기 테스트로 분리.
- 샤드: 쓰기 → 읽기 왕복, 손상 파일 거부, 해시 검증.
- 매칭: 자모 분해, 오독 한 글자 허용, 정확 일치 우선.
- 큐: 우선순위, 체크포인트 재개, 중복 방지.

## 9. 하지 않는 것

- 전체 코퍼스 완주를 목표로 하지 않는다. 순서가 목표다.
- P2P 전송. 포맷만.
- 다른 플랫폼 OCR 1차 구현.
- 페이지 표본 추출(격장 OCR). 재현율을 예측할 수 없어 기본에서 뺀다.
