# tsuburu

hitomi.la를 검색하고 읽는 가벼운 데스크톱 클라이언트.

파일 하나 받아서 실행하면 브라우저가 열린다. Docker도, 따로 깔 런타임도,
처음에 받아야 하는 색인도 없다.

```
$ tsuburu
tsuburu is running at http://127.0.0.1:8420/
press ctrl+c to stop
```

English: [README.md](README.md)

## 왜

이 사이트를 오프라인에서 검색하는 보통의 방법은 색인을 직접 만드는 것이다.
크롤링하고 저장하고 서빙하는 서비스 대여섯 개를 컨테이너로 묶는다. 뭔가 하나
찾아보려는 사람에게 요구하기에는 큰 장치다.

tsuburu는 **hitomi가 이미 서빙하고 있는 색인을** HTTP 범위 요청으로 몇 킬로바이트씩
읽는다. 만들 색인도, 맞출 동기화도 없다.

이 사이트의 인식된 텍스트와 메타데이터를 만들어 배포하는 사람들이 있다. 그런
코퍼스가 있다면 가져와서 아래의 거의 모든 것이 빨라지고 오프라인에서도 되지만,
검색하고 읽는 데 필수는 아니다.

## 무엇을 얼마나 먹나

M4 Pro(macOS 26.5, 24 GB), 가정용 회선에서 측정. 코퍼스·메타 스냅샷·
키워드 그래프를 모두 가져온 상태다.

### 프로그램

| | |
|---|---|
| 바이너리 | **3.9 MB** (프론트엔드가 안에 들어 있다) |
| 프론트엔드 번들 | JS 136 kB, CSS 14 kB — gzip 47 kB |
| 실행부터 첫 응답까지 | **0.4초** |
| 메모리, 놀고 있을 때 | **22 MB** |
| 메모리, 대사 코퍼스를 훑는 동안 | 약 540 MB |
| 메모리, 임베딩 인덱스를 연 뒤 | 2.5 GB — 파일을 메모리 매핑한 것이라 회수된다 |

쓰기 전에는 아무것도 올리지 않는다. 22 MB가 데이터베이스 다섯 개를 연 프로그램
전체이고, 그 위의 숫자들은 특정 검색이 도는 동안 건드리는 양이다.

### 디스크

가져오기로 선택한 것만 차지한다.

| | |
|---|---|
| 아무것도 안 가져왔을 때 | 약 2 MB (즐겨찾기·기록·설정) |
| 인식된 대사, 108,340편 | 1.8 GB |
| 메타데이터 스냅샷, 1,464,390편 | 1.1 GB |
| 키워드 그래프, 106,155편 | 174 MB |
| 임베딩 인덱스, 2,537,826구절 | 2.6 GB — 있는 자리에서 읽고 복사하지 않는다 |
| 받아둔 페이지 | 남긴 만큼. 23쪽 작품 하나가 약 15 MB |

### 속도

hitomi 검색. 대부분이 네트워크 왕복이다.

| | |
|---|---|
| 처음 찾아보는 낱말 | **1.6초** |
| 같은 검색을 다시 | **0.7 ms** |
| 두 낱말 교집합 | 3.8초 |
| 인기순 정렬 | 0.7초 |
| 검색 한 번에 오간 양 | 받음 **5.3 KB**, 보냄 1 KB — 헤더와 TLS 포함 |

코퍼스를 가져온 뒤, 로컬에서:

| | |
|---|---|
| 제목·작가·시리즈·캐릭터 | 146만 편에서 **0.19초** |
| 입력 중 태그 자동완성 | 0.8 ms |
| 한 작가의 작품과 언어별 개수 | 47 ms |
| 무엇에 관한 작품인가 | 1 ms |
| 비슷한 이야기 | 2~18 ms |
| 한 낱말이 관통하는 작품들 | 1 ms |

대사 검색. 108,340편, 인식된 텍스트 1.5 GB 위에서:

| | |
|---|---|
| 기억나는 대사, 정확히 | **1.2초** |
| 잘못 기억한 것까지 감안해서 | 0.7초 |
| 비슷한 장면 | 첫 호출 4.3초, 이후 **0.20초** |
| 의미로 (팩이 떠 있을 때) | 1.5~3.4초 — 대부분이 모델이 문구를 읽는 시간 |

읽기와 색인:

| | |
|---|---|
| 텍스트 인식 | **초당 7.4쪽** |
| 페이지 내려받기 | 1.7 MB/s, 초당 2.5쪽 |
| 대사 코퍼스 가져오기 | 31초 (대부분 이미 있으면 11초) |
| 메타데이터 스냅샷 가져오기 | 4분 |
| 키워드 그래프 가져오기 | 25초 |

hitomi 검색은 계산이 아니라 지연이 대부분이다. 색인이 6~7단 깊이의 B-트리이고
단마다 앞의 결과가 있어야 다음을 요청할 수 있다. tsuburu는 시작할 때 위쪽 단을
배경에서 미리 받아두는데, 그것만으로 70 %쯤이 사라진다. 결과 목록은 지금 페이지에
필요한 만큼만 읽는다.

## 사용법

```
tsuburu                          # 서버를 띄우고 브라우저를 연다
tsuburu serve --port 9000        # 포트 지정 (0이면 빈 포트를 잡는다)
tsuburu serve --no-open          # 브라우저를 열지 않는다
tsuburu search "glasses -school" # 터미널에서 검색
tsuburu gallery 4170351          # 갤러리 하나를 살펴본다
```

낱말은 AND로 묶인다. 앞에 `-`를 붙이면 제외한다. 셸이 플래그로 읽지 않도록 질의
전체를 따옴표로 감싼다.

브라우저에서는 **검색창 하나가 세 곳에 동시에 던진다** — hitomi의 태그, 로컬
제목, 인식된 대사 — 그리고 도착하는 구획부터 채운다. 한 줄로 섞지 않는다. 태그
교집합과 대사의 퍼지 유사도는 같은 자로 잴 수 없고, 섞으면 순서가 임의로
정해지기 때문이다. 각 구획에는 그것만 보는 링크가 있다.

## 오프라인으로 읽기

작품 전체든 한 쪽이든 디스크에 남길 수 있다. 리더에 **다운로드**와 **이 쪽
받기**가 있고, 다운로드 탭이 지금 있는 것과 진행률을 보여주며 마저 받거나 지울
수 있다.

페이지는 hitomi가 이미 주는 해시로 저장한다. 그래서 재업로드본이 같은 페이지를
써도 파일은 하나고, 작품을 지울 때 다른 작품이 쓰는 페이지는 남는다. 받아둔
작품을 읽을 때는 네트워크를 아예 타지 않는다. 이미지 프록시가 디스크를 먼저
보고, 갤러리 정보를 못 받아와도 디스크의 페이지 목록만으로 열린다.

## 작가

갤러리의 작가 이름이 그 사람의 페이지로 간다. 메타 스냅샷에서 최신순으로,
언어별 개수와 함께 나온다 — 읽는 언어에 머무를 수 있게. **팔로우**는 즐겨찾기
옆에 이름을 남기고, 즐겨찾기 탭이 팔로우한 사람과 각자의 작품 수를 보여준다.

작가 페이지는 스냅샷에서 나오므로 `import-meta`를 먼저 돌려야 한다.

## 공개된 코퍼스 쓰기

이 사이트의 인식된 텍스트·메타데이터 스냅샷·키워드 그래프는 공개돼 있다. 그것들이
있다면 명령 셋으로 들어가고, 무거운 일의 대부분이 사라진다.

```
tsuburu import-artifact  /path/to/llm-search-index  # 인식된 한국어 텍스트, 31초
tsuburu import-meta      /path/to/data.db           # 146만 편, 4분
tsuburu import-keywords  /path/to/graph.csv         # 10만 6천 편, 25초
```

서버를 먼저 끈다(redb는 한 프로세스만 연다). `import-meta`는 SQLite 파일을
로컬 `sqlite3` 명령으로 읽는다. macOS에는 들어 있고, 리눅스는 패키지로 있고,
Windows는 sqlite.org의 `sqlite3.exe`가 `PATH`에 있어야 한다.

메타 스냅샷이 있으면 그것이 덮는 갤러리의 카드는 네트워크를 타지 않고, 검색창에
**로컬 제목·작가** 범위가 생겨 한국어 제목·작가·시리즈·캐릭터가 오프라인에서
찾힌다. 스냅샷은 뜬 날에서 멈추지만, 그 뒤 hitomi에서 받아온 갤러리는 볼 때마다
스냅샷에 적어 넣어서 둘러본 만큼은 따라온다.

대사 코퍼스가 있으면 2026년 중반까지의 한국어 갤러리 전부가 기억나는 대사로
찾힌다. 내려받기도 인식도 하지 않는다.

`llm-search-index` 디렉터리는 tsuburu의 저장소로 복사되지 않는다. 임베딩 인덱스는
있는 자리에서 읽으므로 폴더를 그대로 두어야 한다.

## 무엇에 관한 작품인가

`graph.csv`도 함께 공개돼 있다. 인식한 대사에 TF-IDF를 돌려 작품마다 관통하는
낱말을 뽑아둔 것이다. 임베딩 인덱스가 2.6 GB인데 이건 수십 MB다.

작품 화면에 그 낱말들이 뜨고, 각각이 그 낱말이 관통하는 다른 작품들로 이어진다.
리더 아래에는 **비슷한 이야기** 줄이 있고, 두 작품이 무엇을 공유하는지 함께
보여준다. 임베딩보다 거칠지만 — 공유한 의미가 아니라 공유한 낱말이다 — 두는
값이 거의 없고 모델 없이 답한다.

어떤 시리즈의 2권에서 물으면 1권을 답한다. 등장인물 이름 넷을 공유하기 때문이다.
2만 편을 넘는 낱말은 가져올 때 버린다. 저장은 제일 많이 차지하면서 어느 작품도
설명하지 못하기 때문이다. 그런 낱말을 찾으면 "없다"가 아니라 그렇게 말해준다.

## 대사 검색

hitomi의 색인은 제목과 태그만 안다. 기억나는 대사로 작품을 찾으려면 tsuburu가
페이지를 직접 읽어야 한다. 운영체제의 텍스트 인식을 돌리고 그 텍스트를 남긴다.
이미지는 읽자마자 버린다.

**열어본 작품은 보는 대로 읽어둔다.** 그 페이지들은 어차피 화면에 보여주려고
내려온다. 그래서 이미지 프록시가 들고 있던 바이트를 인식기에 그대로 넘긴다.
추가로 받는 것이 없고, 실제로 읽은 작품이 그 안의 한 줄로 찾히게 된다. 이미
텍스트가 있는 페이지는 건너뛰므로 다시 읽어도 비용이 없다. 대사 탭이 이렇게 모인
것을 용량과 함께 보여주고, 하나든 전부든 지운다.

**배경 스윕**은 다른 것이고 **기본 꺼짐**이다. 열어본 적 없는 갤러리를 받기
때문이다. 대사 탭에서 켜면 앱이 열려 있는 동안 인기 있는 한국어 갤러리부터
색인한다. 탭은 항상 얼마나 덮였는지 보여준다. 못 찾았다는 것은 "없다"만큼이나
자주 "아직 색인하지 않았다"는 뜻이다.

좁히는 방법 둘:

- **읽은 기록 가져오기.** 브라우저 기록이나 예전에 쓰던 데이터베이스의 hitomi
  주소·번호를 붙여 넣으면 다른 것보다 먼저 색인한다.
- **골라 담기.** 태그·언어·종류로 좁혀 그것만 담는다.

### 읽은 것 나누기

비싼 것은 텍스트인데 그건 작다. 그래서 옮길 수 있다. 대사 탭이 이 컴퓨터가 읽은
것을 `.tsd` 샤드 파일로 내보내고 남의 것을 가져온다. 파일은 이름에 든 해시로
검증하고, 내보낼 때 직접 골라 읽은 작품은 뺄 수 있다.

### 비슷한 장면

아티팩트에는 구절마다 4B 모델이 만든 임베딩도 들어 있다. 문구로 검색하려면 그
모델이 필요하지만, **이미 색인된 구절로 검색하는 데는 아무것도 필요 없다.** 대사
검색 결과마다 **비슷한 장면** 버튼이 있어, 그 구절에 저장된 벡터로 가장 가까운
구절들을 찾는다. "이것과 비슷하게 읽히는 게 또 뭐가 있나"에 답한다.

어떤 시리즈 2권의 한 쪽에서 물으면 1권의 같은 장면이 1위, 3권이 2위로 나온다.

이 컴퓨터에서 읽은 구절도 팩이 설정돼 있으면 함께 임베딩해서 가져온 인덱스와
나란히 훑는다. 그래서 의미 검색과 비슷한 장면이 가져온 코퍼스뿐 아니라 **내가
읽은 작품에도 닿는다.**

### 의미로 찾기

같은 벡터를 구절이 아니라 *문구*로 검색하려면 그것을 만든 모델이 필요하고,
그건 수 기가바이트짜리 내려받기다. tsuburu는 담지 않고, 담을 필요도 없다. 대사
탭의 팩 설정에 OpenAI 임베딩 API를 말하는 서버 주소를 넣으면 그때 구절 모드가
나타난다. llama.cpp든 Ollama든 LM Studio든, `Qwen3-Embedding-4B`이거나 그와 벡터를
공유하는 모델이면 된다.

```
llama-server -m Qwen3-Embedding-4B-Q8_0.gguf --embedding --pooling last \
             -c 4096 -ub 4096 --port 8080
```

다른 모델은 그럴듯한 벡터를 주고 결과만 쓸모없어진다. 그래서 설정에 **확인**
버튼이 있다. 색인에 이미 있는 구절을 다시 임베딩해 저장된 벡터와 비교한다.
0.9 아래면 코퍼스가 나쁜 것처럼 두지 않고 모델이 다르다고 말한다. 그 인덱스를 만든
모델을 물리면 1.000이 나오고, 질의 하나가 1~3초 걸리는데 그 대부분이
검색이 아니라 모델이 문구를 읽는 시간이다.

## 표시 언어

한국어·English·日本語. 처음에는 브라우저를 따르고, 고른 것을 기억한다. 전환기는
내비게이션 끝과 리더 헤더에 있다.

번역하는 것은 콘텐츠 둘레의 말뿐이다. 제목·태그·대사는 hitomi가 가진 언어 그대로
둔다. 숫자는 브라우저가 아니라 고른 언어의 방식으로 끊는다. 오류는 영어 진단을
그대로 두되 그 위 한 줄 — 무엇을 해야 하는지 말하는 부분 — 은 번역하고, 사용자가
조치할 수 있는 실패는 서버가 이름을 붙여 보내서 그 한 줄이 상황에 맞게 나온다.

언어 추가는 `web/src/lib/locales/` 아래 파일 하나다. 영어 파일에 타입으로 묶여
있어서, 빠진 문구가 있으면 번역된 화면에 영어가 남는 대신 빌드가 깨진다.

## 플랫폼

검색·읽기·즐겨찾기·기록·다운로드·가져오기는 어디서나 된다. 텍스트 인식만 다르다.
tsuburu는 모델을 담지 않고 그 기계가 이미 닿을 수 있는 것을 부르기 때문이다.

| | 인식 | 디코딩 |
|---|---|---|
| macOS | Vision | ImageIO |
| Windows | Windows.Media.Ocr | WIC — AVIF는 무료 AV1 Video Extension이 필요 |
| 리눅스, 그 밖의 유닉스 | `tesseract` | `ffmpeg`, ImageMagick, `avifdec` 중 하나 |

앞의 둘은 운영체제에 들어 있다. 리눅스는 둘 다 없어서 배포판이 패키지로 주는 도구
두 개를 부른다. `import-meta`가 `sqlite3`를 부르는 것과 같은 방식이다.

```
sudo apt install tesseract-ocr tesseract-ocr-kor ffmpeg
```

hitomi가 AVIF로 주는데 leptonica가 그걸 못 읽어서 tesseract 앞에 디코더가 하나
필요하다. 둘 중 하나가 없으면 대사 탭이 **무엇을 깔아야 하는지** 말한다. 고장난
척하지 않는다. 어느 쪽이든 가져온 코퍼스는 그대로 검색된다.

인식 품질은 같지 않다. 같은 한국어 페이지에서 Vision이 읽은 낱말 8개 중
tesseract는 7개를 찾았다. 매칭에는 충분하지만 — 한글 사이 공백을 무시하고 퍼지로
점수를 매기므로 — 줄 단위로는 더 지저분하다.

## 문자 체계를 가리지 않는 매칭

제목과 대사는 한글·라틴·그 밖의 문자를 모두 덮는 하나의 인코딩으로 맞춘다. 그래서
일본어 제목이나 키릴 문자 대사도 한국어와 같은 방식으로 걸린다. 한글 사이 공백은
무시하고 라틴 낱말 사이 공백은 지킨다.

인식기에는 어떤 문자를 볼지 알려준다. 전부 요구하면 정확도가 떨어지기 때문이다.
작품은 그 작품의 언어로 읽고, 대사 탭의 언어 설정은 배경 스윕이 훑을 코퍼스를
고른다.

## 빌드

Rust 1.90+, Node 20+.

```
cd web && npm install && npm run build && cd ..
cargo build --release
```

프론트엔드는 컴파일 시점에 바이너리 안으로 들어가므로 릴리스 산출물은 파일
하나다. `web/dist`는 커밋하지 않는다. 프론트엔드 단계를 건너뛰고 빌드해도
컴파일은 되고, 빈 화면 대신 자산이 없다고 말한다.

## 테스트

```
cargo test --workspace                     # 오프라인. 기록해둔 응답 바이트로 검증
cargo test -p tsuburu-fetch -- --ignored   # 실제 사이트에 붙는다
```

오프라인 스위트는 실제로 받아둔 바이트를 파싱하므로 이상화된 포맷이 아니라 진짜
포맷을 검증한다. 사이트가 바뀌었는지는 라이브 스위트가 알려준다.

## 깨질 때

깨진다. hitomi의 색인 포맷은 문서가 없고 도메인은 이미 한 번 옮겼다
(`ltn.hitomi.la`는 이제 안 뜬다). tsuburu는 읽은 것을 검사해서, 기대한 포맷이
아니면 **사이트가 바뀌었고 업데이트가 필요하다**고 말한다. 틀린 결과나 빈 화면을
보여주지 않는다.

hitomi 포맷에 대한 지식은 전부 `tsuburu-hitomi` 크레이트에 있다. 고칠 곳은 거기
하나다.

## macOS

릴리스에 서명이 없어서 처음 열 때 "개발자를 확인할 수 없음" 경고가 뜬다.
바이너리를 우클릭하고 열기를 고르면 된다.

## 알아둘 것

tsuburu는 전부 이 컴퓨터에서 돈다. 콘텐츠를 호스팅하거나 재배포하지 않는다. 여러분이
보낸 요청만 중계하고, 동시에 보내는 수를 제한한다. 검색하는 사이트에는 성인용
자료가 있고 이 프로그램은 성인용이다.

Ctrl-C나 TERM으로 끄면 데이터베이스가 깨끗이 닫힌다. 강제로 죽이면 다음 실행 때
복구가 돌고, 코퍼스가 다 있는 상태에서 그건 30초와 2 GB짜리 일이다.
